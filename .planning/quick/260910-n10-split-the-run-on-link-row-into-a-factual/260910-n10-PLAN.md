# Split the run-on Link row into a factual Link row plus a separate capability row

## Problem

The property panel's `Link` row concatenates three unrelated claims into one
value string that now wraps to three lines:

```
Link            480 Mb/s (USB 2.1) — could run at
                SuperSpeed 5 Gbps on a faster port
```

Two of those three claims are defects, not just layout:

1. **"on a faster port" is a remedy USBee cannot support.** The reference
   device (Realtek RTL8153 inside a Samsung monitor) is capped by a Genesys
   GL850 USB-2.0-only hub *inside the monitor* — `05e3:0608` at
   `usb 5-2.4.1.1`. No port change can help; the user cannot rewire the
   monitor. Naming the real culprit needs an ancestor-chain walk that exists
   only as a daemon proposal (`link.culprit` / `link.culprit_id`, research
   §6 fault 2/3, §8, §9 phase 1). USBee must therefore state the device's
   capability and stop — the same discipline commit `18aff96` applied when
   `ss-never-linked` / `ss-unstable` / `ss-elsewhere` were withdrawn (see the
   `PEER_STATES_KNOWN` commentary in `src/link-verdict.js`).
2. **`(USB 2.1)` names a spec that does not exist.** `usb_version` is the
   daemon's canonicalised `bcdUSB` (`summary.rs:250 canonical_usb_version`,
   `2.10` → `"2.1"`). `bcdUSB 2.10` means only that the device exposes a BOS
   descriptor; it reads like an actionable version number next to a rate that
   already says the same thing more precisely.

The string is **extension-composed**, not daemon-supplied
(`src/popover.js:451`), so both are fixable here.

## Decisions

- **D1 — new row label: `Capability`.** Reuses the existing translated label
  already bound to `usb_bos_suppressed` (`src/label-table.js:68`), whose value
  is the complementary "unknown — the kernel skips this device's capability
  descriptor". The two are mutually exclusive (a suppressed BOS yields no
  capability figure), so one word covers both states and no new translatable
  label is introduced. Rejected: `Achievable` (the user's sketch — implies the
  speed is reachable somewhere, which is exactly the inference USBee cannot
  make), `Device rating` (collides with "Max bus power" — "rating" reads as a
  power rating), `Rated speed` (ambiguous whether the link or the device is
  rated).
- **D2 — the row states capability and stops.** Value is the daemon's own
  `usb_capable_speed` label, verbatim, exactly as today. No "why", no
  "where", no remedy. Nothing about the cable, port, hub or fixability can be
  backed by data USBee holds.
- **D3 — suppression rule.** Render the row only when it says something the
  Link row does not:
  - `capableText` non-empty, AND
  - `capableMbps > negotiatedMbps` when the numeric twin is present;
  - when `usb_capable_speed_mbps` is absent, fall back to
    `verdict ∈ {BelowCapability, Degraded}` (both mean capable > negotiated
    by BOS spec §6).
  Everything else says nothing — including `AtCapability`, an unknown
  verdict, and a daemon that reports a capability at or below the link.
- **D4 — drop `(USB 2.1)` from the Link row.** The Link row's job is now the
  measured fact; `bcdUSB` is a declared descriptor field, a category
  mismatch. The rate already carries the generation information more
  precisely. `usb_version` stays on the wire and stays rendered in the tile
  title (`src/device-store.js:255`) — correcting *that* needs the speed-tier
  label from research §8 and is deliberately out of scope here.
- **D5 — leave `AtCapability` and `Degraded` Link-row suffixes alone.**
  `— full capability` is short and its Capability row is suppressed anyway.
  `— below the %s this device needs` quotes the *functional floor*, a
  different fact from the capability, and splitting it would collide with the
  existing tech-tier `Needs at least` row.
- **D6 — the boolean lives in `link-verdict.js`.** Structured in, structured
  out; the zero-import contract is what lets CI unit-test it.
