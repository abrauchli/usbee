# Withdraw the false faster-port remedy from the degraded-link notification

## Problem

`src/notifier.js` puts the daemon's `DataRateDegraded` **detail** string
verbatim into the notification body. That string is

```
Device advertises up to 5 Gb/s (Gen 1); move it to a faster port or use a
cable that supports it
```

— usbeehive `src/bos.rs:824`. Its second clause is the same remedy quick
task 260910-n10 just withdrew from the property panel, and it is worse in a
notification, which interrupts rather than waits to be read.

The claim is not supportable. On the reference machine a Realtek RTL8153
gigabit adapter inside a Samsung monitor is held to 480 Mb/s by a Genesys
GL850 (`05e3:0608`) USB-2.0-only hub chip **inside the same monitor**
(`.../scratchpad/cable-diagnostics-research.md` §2, §6 fault 3). No port on
the computer is upstream of that bottleneck. USBee reads no ancestor chain
(§11 "no parent lookups in USBee"), so it cannot know whether a port change
would help.

The precedent is `src/link-verdict.js` `deriveShowCapability()` and its
module header: the device's own BOS capability is a fact about the silicon
and is safe to state; *where* that capability could be reached is an
inference USBee cannot support.

## Decisions

- **D-1 — Do not string-munge the daemon's `detail`.** Splitting it on the
  `;` would fabricate a claim boundary the wire does not define. USBee drops
  the whole string instead and composes its own body under gettext, the same
  discipline `buildLinkBlock()` already states at `popover.js:427-429`.
- **D-2 — Keep the `onDataRateDegraded(id, summary, detail, headline)`
  signature.** `detail` stays accepted and is documented as deliberately not
  rendered; that records the choice for the next maintainer, and
  `tests/forward-compat.test.js:741` pins the signature.
- **D-3 — Keep the daemon's `summary` in the title.** "Linked at 480 Mb/s —
  below the 5 Gb/s this device needs" is a measurement, not a remedy.
- **D-4 — The notification keeps firing, at `Urgency.NORMAL`, persistent and
  coalesced.** See rationale below.
- **D-5 — Withdraw the panel's `Fix` row entirely** rather than reword it.
  There is no true remedy to put in its place, and the `Detail` row already
  carries the honest candidate list when the SuperSpeed shape applies.

### D-4 rationale (the "should it fire at all" call)

- The gate is daemon-asserted `Degraded` = `negotiated < functional_floor`,
  i.e. the **vendor's own** `bFunctionalitySupport` says the device will not
  work properly at this speed. That is a malfunction report, not advice.
  `BelowCapability` never reaches the notifier.
- It fires at plug time, when the user is holding the cable and is best
  placed to try something. USBee cannot promise a swap helps; the user, who
  can see their own desk, can decide. Stating the fault and leaving the
  remedy to the person with the topology knowledge is exactly the division of
  labour the panel adopted.
- `Urgency.LOW` was considered and rejected: gnome-shell 48's
  `_onNotificationRequestBanner` returns early for `LOW`, so the banner never
  appears and the item is filed silently in the tray. That would trade a
  false remedy for a false calm — a gigabit adapter silently stuck on USB 2
  is precisely the "why is my network slow?" question USBee exists to answer.
- Research rev 2 §8 is explicit: "Warning policy unchanged: `Degraded` stays
  as is (BOS spec §6)", with the softer, default-off notification tier
  reserved for the future `link.fixable` suggestions. Softening `Degraded`
  now would pre-empt a daemon-side decision with no new evidence.
- The per-device mute and Open Preferences actions already give anyone who
  disagrees a one-click exit.

### Action buttons

Audited: `"Don't notify for this device again"` / `"Don't notify for this
port again"` / `'Open Preferences'`. None is remedy-shaped — they describe
what the button does to USBee, not what the user should do to the hardware.
**Unchanged.**
