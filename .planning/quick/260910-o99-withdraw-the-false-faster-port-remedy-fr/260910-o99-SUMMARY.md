**Audited and clean, deliberately:**

- `onCapabilityDegraded()` (charging) still renders the daemon's `detail`
  verbatim. Every charging string usbeehive composes is an observation, not a
  prescription — usbeehive `src/diagnostic.rs:96, 112, 123, 134` ("Cable rated
  for 60W, but charger can deliver 100W", "…often the device's own policy…").
  A comment at the assignment records the audit and asks for a re-check if the
  daemon's charging copy changes.
- The daemon's `data_rate` prose reached the user through **exactly one**
  surface — the notification body. `grep data_rate usbee@bitcreed.us/src/*.js`
  returns only `popover.js:428`, a comment explaining that `buildLinkBlock()`
  deliberately composes from tokens instead.
- Action buttons: `"Don't notify for this device again"`, `"Don't notify for
  this port again"`, `'Open Preferences'`. None is remedy-shaped — each names
  what the button does to USBee, not what to do to the hardware. Unchanged.

## 2. Final strings

**Notification (DataRateDegraded), unchanged title:**

```
%s — %s          headline + the daemon's `summary`,
                 e.g. "Realtek RTL8153 — Linked at 480 Mb/s — below the
                       5 Gb/s this device needs"
```

**Notification body, new, USBee-composed under gettext:**

```
The cause could be the cable, the port, or a hub in between
```

**Property panel:** no `Fix` row at all. The Link / Capability / Detail rows
are untouched.

### What is deliberately no longer claimed

- That moving the device to another port would help.
- That changing the cable would help.
- That any specific component is at fault — the body names three candidates
  and stops.
- A side effect worth stating: the daemon's factual half ("Device advertises
  up to 5 Gb/s (Gen 1)") went with the remedy, because splitting the daemon's
  sentence on its `;` would invent a claim boundary the wire does not define.
  Nothing is lost to the user: the title already carries both the achieved
  rate and the rate the device needs, and the panel still shows the
  **Capability** row with the device's own rating.

**Why the body is exhaustive without topology:** `Degraded` means the
device's own descriptor advertises more than it negotiated, so by its own
account the device is not the limit; everything else on a USB path is the
cable, the receptacle or an intervening hub.

## 3. Should it fire at all — the call

**It keeps firing, unchanged: `Urgency.NORMAL`, persistent, coalesced by
device id, self-dismissing on `DataRateRestored`, 2.5 s daemon-appear
suppression, per-device mute.** Reasons, in order of weight:

1. **The gate is a malfunction report, not advice.** `Degraded` is
   `negotiated < functional_floor` — the device's own `bFunctionalitySupport`
   declaring it will not work properly at the speed it got. `BelowCapability`
   never reaches the notifier. The remedy was never what made the event worth
   raising.
2. **It fires at plug time**, when the user is holding the cable and is the
   only party who can see their own desk. Stating the fault and leaving the
   response to the person with the topology knowledge is exactly the division
   of labour `deriveShowCapability()` adopted for the panel.
3. **`Urgency.LOW` was considered and rejected.** Verified against the
   installed gnome-shell 48 (`gresource extract /usr/lib/gnome-shell/
   libshell-18.so /org/gnome/shell/ui/messageTray.js`,
   `_onNotificationRequestBanner`, line 926): `if (notification.urgency ===
   Urgency.LOW) return;` — LOW shows **no banner at all** and is filed
   silently in the tray. A gigabit adapter silently stuck on USB 2 is
   precisely the "why is my network slow?" question USBee exists to answer;
   hiding it would trade a false remedy for a false calm.
4. **Research rev 2 §8 is explicit**: "Warning policy unchanged: `Degraded`
   stays as is (BOS spec §6)", with the softer, *default-off* notification
   tier reserved for future `link.fixable` **suggestions**. Softening
   `Degraded` now would pre-empt a daemon-side decision with no new evidence.
5. Anyone who disagrees has a one-click exit already.

Persistence stays for the same reason it was chosen: the notification mirrors
a live condition and is destroyed by `DataRateRestored`, which is what a
resident notification is for.

## 4. Action buttons

**No change.** Audited (§1) and none is remedy-shaped. The `_muteById()`
docstring was corrected: keying the mute on the topological id means a replug
elsewhere yields a different id the mute does not cover — a statement about
how ids are formed, previously written as though a faster port were a cure.

## 6. Blocked on usbeehive

- **The daemon still composes the remedy** at usbeehive `src/bos.rs:824`.
  USBee drops it, but any other consumer of `DataRateDegraded` /
  `SnapshotJson` still receives it. Fixing it at source is a change in the
  sibling repo.
- **Naming the actual culprit** — `link.culprit`, `link.culprit_id`,
  `link.action`, `link.fixable`, `topology.hub_depth` (research §8, §9
  phase 1). Until those land, no surface can say more than "the cable, the
  port, or a hub in between".
- **Socket-level copy** stays withdrawn pending `port.peer_source` /
  `port.peer_confidence` (research §5, §8) — unchanged by this task.
- **The softer suggestion tier** (`link.fixable`, amber-lite row, default-off
  notification) is where advice-shaped events belong once the daemon can back
  them. That is the natural moment to revisit §3's call.

## 7. Inferred — worth a human audit

- **Claim #3 (alt-mode PD) was left standing.** The judgement: unlike the link
  case, the daemon *names the cause* (`no_usb_pd` on this connection), so
  "use a USB-C port and cable that support Power Delivery" follows an
  asserted fact rather than absent topology — and a Billboard device reporting
  `Unsuccessful` is very often simply on a USB-A-to-C cable, where the advice
  is correct. It is still, strictly, a remedy USBee cannot verify would work.
  Flagging it rather than deciding it unilaterally.
- **`_detail` retained in `onDataRateDegraded`'s signature** rather than
  removed from the call chain. Kept so `dbus-client.js` stays a faithful
  reading of the wire and so the deliberate drop is visible at the boundary;
  `tests/forward-compat.test.js` pins the new signature.
- **§3's "keep firing at NORMAL"** is a product call made from the artifacts
  (research §8, the BOS spec's Degraded semantics) rather than from user
  feedback. It is the one decision here that is a preference rather than a
  correctness fix.
- **The body sentence's exhaustiveness** ("cable, port, or a hub in between")
  assumes the device's own BOS advertisement is truthful, which is what makes
  "the device is not the limit" hold. A lying descriptor would make the
  sentence incomplete — but it would equally break `Degraded` itself, which
  is daemon-owned.
