<objective>
Colour-code the displayed speed rating by the daemon's own `usb_link_verdict`,
so "is this the fast port?" is answerable at a glance without reading text.

Purpose: USBee's core value is a glanceable answer. Today the verdict is
carried only in prose (`full capability`, `linked at 480 Mb/s`,
`%s — full capability`), which the reader must find and parse. A three-value
colour scale over the *same* verdict adds a pre-attentive channel while leaving
every word intact.

Output: one pure exported helper in the zero-import `link-verdict.js`, three
colour-only CSS rules, two popover call sites, a conditional third call site on
the Quick Settings tile subtitle, and unit tests covering all five verdict
cases including the red path that has no live example.

This is a straight translation of an existing daemon verdict. **No new
judgment is derived anywhere** — see `<hard_constraints>`.
</objective>

<hard_constraints>
Carried verbatim from the task spec. Each is a blocking condition, not advice.

1. **Do not synthesise the verdict.** `usb_link_verdict` is the only input.
   Deriving a warning or a colour from `usb_capable_speed_mbps > link_speed_mbps`
   is forbidden by the BOS consumer spec (quoted in `link-verdict.js` lines
   18-24). In particular **do not add any ratio rule** such as "12 Mbps but
   capable of 480 ⇒ red" — that was considered and explicitly rejected by the
   user. The existing negative guard at `tests/forward-compat.test.js:1243-1244`
   already tests for this and must keep passing.
2. **Do not widen Tier 0.** `hasLinkIssue()` in `link-verdict.js` stays
   byte-unchanged. `BelowCapability` is deliberately not a fault (decision
   260910-n10; see the `buildLinkBlock` docstring at `popover.js:904-916`).
   Colouring it orange is a *legibility* change, not a promotion to fault:
   the amber left-border `.usbee-row-warning`, the issue-first sort and the
   tile issue tier are all gated on `hasIssue()` and none of them move.
3. **Do not reuse `.usbee-detail-warning`.** It carries unrelated
   charging-warning semantics (charging diag, trust, alt-mode power rows) even
   though it shares the orange value. New classes only.
4. **Colour must not be the sole cue.** Do not remove, shorten or reword any
   text to make room for colour. Zero string changes in this task.
5. **No new gettext strings.** If one turns out to be needed, stop and
   regenerate `po/usbee@bitcreed.us.pot` with CLAUDE.md's exact invocation
   (`prefs.js` first, no `--package-version`) and report the msgid delta. The
   expectation is that `po/` is untouched.
6. **Keep new testable logic in `link-verdict.js`.** That module has ZERO
   imports, which is what lets bare-gjs CI unit-test it; `device-store.js`
   imports the gnome-shell extension resource for gettext and cannot load
   under bare gjs (`.github/workflows/ci.yml:49-62` says so). Precedent:
   260915-ikd and 260917-hkf both moved pure helpers across for this reason.
7. **Do NOT pack or install the extension.** CLAUDE.md documents that
   `gnome-extensions install --force` destroys a symlinked dev checkout
   (260910-hrj). There is no pack step and no install step in this plan.
   Unit tests plus `node --check` are the verification ceiling.

- **ID-01 — Two popover surfaces are coloured, not one.** The task spec says
  "the speed/rate label ... start from `buildLinkBlock`". There are in fact two
  speed labels in the popover: the trailing rate caption on the *collapsed* row
  (`popover.js:681-698`, class `.usbee-row-rate`) and the Link row *value* in
  the expanded detail panel (`buildLinkBlock`, `popover.js:951`). The collapsed
  caption is the genuinely glanceable one — it is visible without expanding
  anything — and the Link row is the one the spec names. Colouring one and not
  the other would make the same device read differently depending on whether it
  is expanded, which is the exact inconsistency the spec's surface-2 rationale
  objects to. Both get the colour.

- **ID-02 — In the detail panel the colour goes on the VALUE label, and the
  existing key-label amber is left alone.** `buildPropertyRow` returns
  `[keyLbl, valLbl]` (`popover.js:1282-1302`) and `buildLinkBlock` currently
  puts `.usbee-detail-warning` on `get_children()[0]` — the KEY. The key-label
  amber is a panel-wide "this row is a warning" convention shared by four other
  rows (charging diag, detail, trust, power). The verdict colour is a different
  scale, so it takes the other column. This is the same "compose across COLUMNS
  instead of competing in one" principle the stylesheet already records for
  `.usbee-pdo-active` / `.usbee-pdo-max` (`stylesheet.css:166-180`).

- **ID-03 — On the collapsed caption the verdict class and the existing
  `isWarning` amber are mutually exclusive, verdict first.** `link.isWarning`
  is deliberately BROADER than `verdict === 'Degraded'`: it also fires on
  `usb_link_degraded == 'true'` with an *unrecognised* verdict, as a
  forward-compat safety net (`link-verdict.js:221-226`). So the caption applies
  `verdictStyleClass(link.verdict)` when that is non-empty, and falls back to
  the existing amber branch otherwise. Exactly one colour class on the label in
  every case, the safety net preserved, and no cascade race between two `color`
  declarations.

- **ID-04 — `Degraded` renders red where the collapsed caption previously
  asked for amber.** That is what the spec's mapping table says. Note this is
  not even a visible change today: **the existing amber on that caption is a
  silent no-op** — `.usbee-detail-warning` sits at `stylesheet.css:148` while
  `.usbee-row-rate` sets `color` at line 185, both single-class selectors, so
  the later rule wins and the caption renders dim-white for a degraded device
  right now. Appending the verdict rules at the end of the file is what makes
  the colour actually render. **The pre-existing no-op on the unrecognised-
  verdict fallback path is NOT fixed here** — fixing it would change the
  treatment of a device shape no live hardware exhibits and that this task did
  not ask about. Record it in the SUMMARY as a separate finding.

- **ID-05 — `verdictStyleClass()` is total and takes the verdict alone.** Any
  input that is not one of the three known strings — `null`, `undefined`, `''`,
  a future daemon value, a non-string — returns `''`. This matches the
  "'' when there is nothing to say" convention `formatRate()` and
  `formatCapabilityBrand()` already set in the same module, so callers need no
  null-check discipline they do not already have. It runs inside gnome-shell's
  own process, so it must not be able to throw (same rule `formatUsbId()`
  records at `link-verdict.js:450-451`).

- **ID-06 — Class names.** `.usbee-link-at-capability`,
  `.usbee-link-below-capability`, `.usbee-link-degraded`, as the spec suggests.
  The `usbee-link-` prefix ties them to the Link concept and keeps them clear of
  the `usbee-detail-` and `usbee-row-` families.

- **ID-07 — The palette values are locked and the light-theme contrast is
  accepted, not corrected.** Measured at planning time against the Shell's own
  shipped theme backgrounds (extracted from
  `/usr/share/gnome-shell/gnome-shell-theme.gresource`: light popover
  `#fafafb`, dark popover `#36363a`), the WCAG contrast ratios are:

  | Colour | vs light `#fafafb` | vs dark `#36363a` |
  |---|---|---|
  | `#2ec27e` green | **2.20** | 5.23 |
  | `#e5a50a` orange | **2.07** | 5.57 |
  | `#e01b24` red | 4.63 | **2.49** |

  Each colour is below AA on one of the two themes. This ships anyway: the
  values are locked by the spec, the text always states the condition
  independently (constraint 4), and the project already ships `#e5a50a` as
  text colour in two places (`.usbee-empty-state-status`,
  `.usbee-detail-warning`). Do **not** substitute darker Adwaita variants
  (`#26a269` / `#cd9309`) — the stylesheet has no light/dark branching
  mechanism today (it hardcodes `rgba(255,255,255,…)` in five places, i.e. it
  assumes dark), so a theme-aware palette is a larger change. Task 2 re-derives
  these numbers as a verification step and the SUMMARY records them plus the
  deferred theme-aware-variant follow-up.
