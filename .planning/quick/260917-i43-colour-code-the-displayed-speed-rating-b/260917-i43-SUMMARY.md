# Quick Task 260917-i43: Colour-code the displayed speed rating by verdict — Summary

The daemon's own `usb_link_verdict` now drives a three-value colour scale on
all three speed surfaces — the collapsed row's rate caption, the detail
panel's Link row value, and the Quick Settings tile subtitle — so "is this
the fast port?" is answerable pre-attentively. **Not one word of text
changed**: the colour is an additional channel over prose that every surface
still states independently.

## Task 3 gate outcome: **PASSED** — implemented, with evidence

The tile subtitle is coloured using **public API on an object USBee owns**.
The gate's three prohibitions are all clear, and a test asserts each:

- **No `_`-prefixed Shell member.** `_applyVerdictClass()` calls
  `this.add_style_class_name()` / `this.remove_style_class_name()` — documented
  `St.Widget` methods — on USBee's own `QuickMenuToggle` subclass. The
  verify-gate grep for `_subtitle|_title` over tile.js's non-comment lines
  returns **0**, as at HEAD.
- **No `get_children()` indexing** in tile.js at all (asserted), and no
  `Main.panel._*` (asserted).
- **The route is a stylesheet class name, not a private JS member.** Verified
  on the **installed Shell 50.1**, not from planning notes: `gresource extract`
  of `/usr/share/gnome-shell/gnome-shell-theme.gresource` shows
  `.quick-toggle .quick-toggle-subtitle` at **gnome-shell-dark.css:2090** and
  **gnome-shell-light.css:2091**, setting `font-weight` (and `font-size` via
  the shared caption rule at :398) and **no `color`** — nothing to fight.
- **Graceful degradation.** If a future Shell renames the class, the selector
  matches nothing and the line renders in its normal colour. Never a crash,
  never a wrong colour.

As the plan noted, `quickSettings.js` itself is not extractable from any
installed gresource here, so the decision rests on `gjs.guide`'s documented
surface plus the extracted theme — not on Shell JS source.

## Deviations from plan

### 1. [Rule 1 — bug prevented] A separate `usbee-tile-*` class family

**Plan said:** device-store Tier 2 carries `verdictStyleClass(cap.verdict)` —
i.e. the tile reuses the popover's three class names.

**Why that would have been wrong:** the popover classes are *flat* `color`
rules, correct when the class lands directly on the label being coloured. On
the tile the class must land on the **toggle** (the only object USBee owns),
and the extracted theme shows `.quick-toggle .quick-toggle-title` sets
`font-weight`/`font-size` and **no `color`** (`gnome-shell-dark.css:390`) — so
the title would have **inherited** the verdict colour, painting the capability
brand (`USB 5Gbps`) green/orange/red. That says something the verdict does
not: the brand is what the hardware *is*, the verdict is about what the link
*is doing*.

**What was done instead:** one `VERDICT_STYLE_SUFFIXES` table, two thin
exports (`usbee-link-*` flat, `usbee-tile-*` descendant-scoped to
`.quick-toggle-subtitle`). The recognised set and the suffixes stay
single-sourced, so the two families cannot drift; a test asserts they are
disjoint, and that no `usbee-tile-*` rule is ever a flat `{`-rule.

### 2. [Rule 1 — verification bug] Hex values removed from the popover docstring

The plan asked the `buildLinkBlock` docstring to "name its colour" per row
*and* asked for a guard that none of the three hex values appears anywhere in
popover.js. Both, literally, are contradictory. Resolved in favour of the
guard (the stronger artifact): the docstring names GREEN / ORANGE / RED and
records that the hexes live only in the stylesheet.

Nothing else deviated. All seven pre-flagged inferred decisions (ID-01…ID-07)
were honoured as written.

## Findings

### The pre-existing cascade no-op — found here, deliberately NOT fixed

`.usbee-detail-warning` (`stylesheet.css:148`) loses to `.usbee-row-rate`
(`:185`): both are single-class selectors setting `color`, so the later rule
wins. The collapsed caption's amber has therefore **never rendered** — a
degraded device's caption showed dim white. Appending the new rules at the
end of the file is what makes the verdict colour actually render.

The amber **fallback** path (an unrecognised verdict with
`usb_link_degraded == 'true'` — the forward-compat safety net) is still a
no-op after this task, and was left that way on purpose: fixing it changes
the treatment of a device shape no live hardware exhibits and that this task
did not ask about. Confirmed still present at the same two line numbers.
**Scope-flagged for a follow-up.**

### The red `Degraded` path has no live example

No device on the reporting machine reports `Degraded`. The red path is
covered by **unit test only** (both the bare-token and `deriveLinkInfo`
routes, plus the tile's `deriveCapabilityTile` route); a test asserts the
live population contains no `Degraded` entry so this stays visible.

### Deferred: a theme-aware palette

Fixing the three below-AA readings needs light/dark branching that
`stylesheet.css` does not have today — it hardcodes `rgba(255,255,255,…)` in
five places, i.e. it assumes dark throughout. That is a larger change than
this task, and is recorded here rather than half-done.
