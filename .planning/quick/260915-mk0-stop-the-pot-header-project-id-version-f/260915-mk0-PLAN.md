# Quick Task 260915-mk0 — Stop the `.pot` header version from drifting

## Problem

`po/usbee@bitcreed.us.pot` carries `Project-Id-Version: USBee 2.7.1` while
`usbee@bitcreed.us/metadata.json` is at `"version": 13, "version-name": "2.8.0"`.
The drift is structural, not an oversight: nothing in the release process bumps
the template header, and quick task 260915-ikd (decision D-14) explicitly
preserved the recorded `xgettext` invocation — `--package-version=2.7.1` and all
— rather than touch it, flagging the stale header for a later task. This is that
task.

## Decision

**Remove the version from the header, keep the field.** Target state:

```
"Project-Id-Version: USBee\n"
```

`Project-Id-Version` is free-form metadata. `msgfmt` and the gettext runtime
never read it; it exists so translation platforms (Weblate, Transifex, Damned
Lies) can label an upload. USBee is English-only, is on no translation platform,
and is not submitted to EGO. A field that nobody consumes but everybody must
remember to bump is a maintenance trap — it has already drifted once. Deleting
the number removes the trap without removing the field.

The fix must land in **both** the committed `.pot` and the invocation that
generates it, or the next regeneration reintroduces the drift.

## Evidence gathered before planning (all under `rtk proxy`)

- **Nothing consumes the field.** `grep -rn "Project-Id-Version|package-version|package-name"`
  over the whole repo (minus `.git`) hits only the `.pot` itself and
  `.planning/` prose. `.github/workflows/release.yml` reads `version-name` from
  `metadata.json` only. `.github/workflows/ci.yml` runs `shexli` against
  `usbee@bitcreed.us/` — `po/` is outside that package dir — plus four `gjs`
  test files. There is no Makefile, no `package.json`, no shell script in the
  repo. No test under `tests/` mentions the `.pot`.
- **Dropping `--package-version` yields exactly the target line.** Probed:
  `xgettext --from-code=UTF-8 --package-name=USBee -o <scratch>/probe.pot …`
  emits `"Project-Id-Version: USBee\n"`. The package name still comes from
  `--package-name=USBee`, so the `# … same license as the USBee package` comment
  on line 3 is unchanged too.
- **The regenerated body is byte-identical to the committed one.** `diff -u`
  between the committed template and the probe shows two changed lines, both in
  the header: `Project-Id-Version` and `POT-Creation-Date`. 162 `msgid` lines on
  both sides. No msgid added, removed or reordered.

## Tasks

1. **Install the regenerated template.** Replace `po/usbee@bitcreed.us.pot` with
   the output of the canonical invocation minus `--package-version`, keeping the
   load-bearing input order (`prefs.js` first, then `src/*.js` — 260910-nge).
   Regenerating rather than hand-editing proves the corrected invocation
   reproduces the target byte-for-byte.
   - verify: `diff` against the pre-change file shows only the two header lines;
     `grep -c '^msgid '` still 162; `msgfmt --check-format` clean.
2. **Fix the recorded invocation in `CLAUDE.md`.** The Development Tools table
   (line 77) still shows a generic `xgettext … *.js` that does not match what the
   project actually runs. Replace it with the real invocation, without
   `--package-version`, and add a `### Regenerating the translation template`
   subsection to the Release Process recording the command, the mandatory input
   order, and the no-version policy so nobody re-adds the number.
   - verify: `grep -rn "package-version" CLAUDE.md` returns nothing.
3. **Run the full suite.** Four `gjs` suites, 483 assertions, must stay green.

## Out of scope

- `metadata.json` stays at `13` / `2.8.0`. No version bump, no tag, no push.
- Historical `.planning/quick/*/PLAN.md` and `SUMMARY.md` files keep their
  verbatim `--package-version=2.7.1` invocations. They are dated records of what
  was run at the time; rewriting them would falsify the provenance trail.
  `CLAUDE.md` is the forward-looking source of truth and the only file a future
  regeneration is read from.
- `CHANGELOG.md` gets no entry. The change is invisible to users of the
  extension — no string, no behaviour, no packaging output differs.
- `gnome-extensions install` is NOT run: the installed path is a real directory
  holding the released v2.8.0 and installing would overwrite the user's working
  install.
