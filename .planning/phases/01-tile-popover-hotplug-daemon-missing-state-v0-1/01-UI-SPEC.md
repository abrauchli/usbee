# Phase 1 — UI Design Contract

> Visual and interaction contract for the GNOME 46+ Quick Settings tile and its popover. Pure-GJS Shell extension hosted inside `gnome-shell`. No web framework, no GTK4/libadwaita in this phase (those are reserved for Phase 2's `prefs.js`, which runs in a separate process).
>
> **Source of truth for design tokens:** GNOME Shell's stock Adwaita stylesheet at `resource:///org/gnome/shell/theme/gnome-shell.css` (and its dark variant). USBee inherits everything from it; this contract enumerates the **few** custom decisions Phase 1 makes on top.
>
> Generated by `gsd-ui-researcher` after reading CONTEXT.md (D-01..D-19 locked), RESEARCH.md (file layout, headline algorithm, paste-ready code), and PROJECT/REQUIREMENTS/PITFALLS docs. Verified by `gsd-ui-checker`.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Shell extension — design system is the host) |
| Preset | not applicable |
| Component library | GNOME Shell built-in `St`, `Clutter`, `PopupMenu`, `QuickSettings` modules (resource:///org/gnome/shell/ui/*.js) |
| Icon library | Adwaita symbolic icon set (system-provided; no bundled icons in Phase 1 except optional `usb-symbolic.svg` fallback per CONTEXT.md Discretion) |
| Font | Cantarell (Shell default; do not override) |

**Rationale (locked by CONTEXT.md D-17 + STACK.md):** USBee runs inside the `gnome-shell` process. The Shell-side UI **must** use `St` widgets and `PopupMenu` primitives; `Gtk` / `Adw` are explicitly forbidden in any file under `extension.js` / `src/*.js`. The "design system" is therefore the host Shell theme — light or dark per the user's GNOME setting, switched automatically.

**No shadcn / no Tailwind / no npm / no cargo:** Phase 1 ships zero external packages (RESEARCH.md §Package Legitimacy Audit). The deliverable is a flat zip built by `gnome-extensions pack`.

## Focal Point & Visual Hierarchy

Anchor: `<a id="hierarchy"></a>`

**Primary focal point** (what the user's eye lands on):

1. **Collapsed state (Quick Settings panel):** the **tile subtitle** is the differentiating focal element. It carries the live answer ("Charging: 65 W in", "USB 3.2 · 10 Gb/s", "Nothing connected"). The tile title ("USBee") is secondary; it exists for tile identity, not information.
2. **Open popover (devices present):** the **first device row's headline** is the focal element. Rows are read top-to-bottom in daemon snapshot order (no client-side reordering in Phase 1).
3. **Open popover (no devices, daemon running):** the **single "No USB devices attached" row** is the focal element; centred horizontally by Shell defaults.
4. **Open popover (daemon NOT running):** the **selectable `St.Entry` containing the systemctl command** is the focal element, because that's the only actionable affordance — the user must copy it. The hint label above it is secondary.

**Hierarchy within a device row** (RESEARCH.md §Example 5 + CONTEXT.md D-12):

```
┌───────────────────────────────────────────────────┐
│ Anker PowerLine 65 W Charger                       │  ← PopupMenuItem.label (top line, default weight)
│   USB-C · USB 3.2 Gen 2 · 10 Gb/s                  │  ← St.Label bullet 1
│   Source — Charging at 65 W                        │  ← St.Label bullet 2
│   Cable limited to USB 2.0 — swap for a            │  ← St.Label bullet (diagnostic, may wrap)
│   full-featured cable to reach 10 Gb/s             │  ← (continued, line_wrap = true)
└───────────────────────────────────────────────────┘
```

- Top line = daemon-supplied `DeviceEntry.headline` (product name, e.g. "Anker PowerLine 65 W Charger"; or "USB-C Port 1" for empty ports).
- Subsequent lines = `DeviceEntry.bullets[]` rendered **verbatim** as separate `St.Label` widgets, in array order. The daemon decides what each bullet says (USB version, link speed, data role, power role, live wattage, diagnostic). USBee adds **zero** formatting beyond line-wrap.
- Diagnostic strings (DIAG-01, DIAG-02) appear as ordinary bullets — they are not visually distinguished in Phase 1. Distinguishing them (e.g. amber accent for warnings) is **deferred to Phase 2 NOTIF** when the daemon's `is_warning` boolean from `Diagnose` is consumed.

**Iconography:**
- **Panel + tile + popover header:** `network-usb-symbolic` (preferred) with `usb-symbolic` as fallback if the theme lacks it. **One symbolic icon for all states in Phase 1.** No degraded-state icon variant (CONTEXT.md Open Question 4 default: "same symbolic + amber subtitle"; amber subtitle is deferred to Phase 2 along with `CapabilityDegraded` subscription).
- **No per-row icons in Phase 1.** The daemon supplies an `icon` field per `DeviceEntry`, but Phase 1 ignores it (RESEARCH.md §Daemon Wire Shape). Per-row icons land when `populateDeviceRows` is refactored to use `PopupImageMenuItem` — deferred to a v1.x polish pass.

## Spacing Scale

Anchor: `<a id="spacing"></a>`

Declared values (multiples of 4, used in custom CSS only — everything else inherits Shell defaults):

| Token | Value | Where used |
|-------|-------|------------|
| xs | 4px | Vertical gap between bullets inside a device row body |
| sm | 8px | Vertical gap between empty-state title, hint, and `St.Entry` |
| md | 16px | Reserved — not used in Phase 1 custom CSS |
| lg | 24px | Reserved — Shell defaults handle popover padding |

**Exceptions:** none. The Shell's own stylesheet sets popover padding, row height (~30px for PopupMenuItem), tile height (40px for QuickMenuToggle), and inter-row gaps. **USBee custom CSS must not override Shell-controlled metrics** (CONTEXT.md anti-feature: "In-tile theming / colour customisation — Quick Settings tiles use Shell theming by design"). The four tokens above appear only inside `.usbee-device-row`, `.usbee-empty-state`, `.usbee-empty-state-body`, and `.usbee-empty-state-entry` rules in `stylesheet.css`.

**Concrete custom-CSS spacing (paste-ready for executor):**

```css
.usbee-device-row .body StLabel + StLabel { padding-top: 4px; }
.usbee-empty-state-body                    { spacing: 8px; }
.usbee-empty-state-entry                   { margin-top: 4px; }
```

(`spacing` is the `St.BoxLayout` token; `padding-top` is standard CSS — both resolve to 4px / 8px multiples.)

## Typography

Anchor: `<a id="typography"></a>`

USBee inherits the Shell font stack (Cantarell). Phase 1 declares **exactly 3 type roles** (≤ 4 cap), **exactly 2 weights** (regular + bold for the row headline only, inherited from `.popup-menu-item .label`).

| Role | Size | Weight | Line height | Where used |
|------|------|--------|-------------|-------------|
| Tile title + subtitle | 14px (Shell `.quick-toggle .title` / `.subtitle`) | 400 | 1.4 (Shell default) | `USBeeToggle.title` ("USBee") + `USBeeToggle.subtitle` (live headline string) |
| Row headline | 14px (Shell `.popup-menu-item .label`) | 600 (semibold, inherited from Shell) | 1.4 | `PopupMenuItem.label.text = device.headline` + empty-state title |
| Body / bullet / hint | 13px (Shell `.popup-menu-item .body` ≈ 0.9em) | 400 | 1.5 (line-wrap on `St.Label`) | All `St.Label` bullets + empty-state hint |

**Monospace exception** (one role, used in exactly one widget):

| Role | Size | Family | Where used |
|------|------|--------|-------------|
| Command field | 13px | `monospace` (Shell falls back to its monospace stack) | `.usbee-empty-state-entry` `St.Entry` text |

**Why monospace for the `St.Entry`:** the user is meant to read the systemctl command character-by-character and copy it without ambiguity (e.g. distinguish `-l` from `-1`). Monospace eliminates a class of "did I read that right?" errors. This is one custom CSS rule, not a global override.

**Paste-ready typography custom CSS:**

```css
.usbee-empty-state-entry StEntry,
.usbee-empty-state-entry { font-family: monospace; font-size: 13px; }
```

**What we do NOT declare:** explicit colors for typography, explicit font sizes for the device row bullets (we inherit Shell's `.popup-menu-item .body` rules), or any custom font weights. The Shell theme owns those.

## Color

Anchor: `<a id="color"></a>`

USBee uses **the Shell's color tokens unmodified** for 60% and 30%. The 10% accent is reserved for **exactly one element** in Phase 1.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Shell `@theme_bg_color` (popover surface — light `#fafafa` / dark `#242424`, theme-switched automatically) | Popover background, tile background |
| Secondary (30%) | Shell `@theme_fg_color` (primary text colour) | Headlines, bullets, hint text, command-field text |
| Accent (10%) | Shell `@accent_color` (default GNOME blue; user-customised since GNOME 47) | **Reserved for: focus ring on the empty-state `St.Entry` only.** That `St.Entry` is the only focusable, user-actionable widget in Phase 1; the accent draws the eye to it when the daemon is missing and the popover opens. |
| Destructive | not used in Phase 1 | Phase 1 contains zero destructive actions (no buttons that spawn subprocesses, no delete affordances — CONTEXT.md D-13). |

**Accent reserved for:** focus ring on `.usbee-empty-state-entry` (when keyboard-focused for copy/select). This is **automatic** — Shell renders focus rings via `@accent_color` on any `:focus` selector. USBee does not write a custom focus-ring rule; it relies on `:focus` styling from the Shell theme to do exactly this and nothing else. **Accent is NOT used for** device-row diagnostics, warnings, "fast port" highlights, or any visual differentiation between device categories — those are explicitly deferred to v1.x / v2.

**Theme adaptivity:** every color above resolves at Shell-theme-switch time. Light theme → light surface; dark theme → dark surface. USBee defines **no hex literals** in `stylesheet.css`. Confirmed against PROJECT.md anti-feature ("In-tile theming / colour customisation — Quick Settings tiles use Shell theming by design").

**Why no semantic warning colour:** PROJECT.md's `CapabilityDegraded` warning notifications (and any per-row amber-subtitle treatment) are 100% in Phase 2 scope. Phase 1 must not introduce a "degraded" colour token because no widget yet consumes it; introducing one now would be design debt the auditor flags later.

### Primary CTA

Anchor: `<a id="primary-cta"></a>`

**There is no traditional "Primary CTA" button in Phase 1.** This is a glanceable indicator, not a form. The closest equivalent is the **selectable command in the empty-state `St.Entry`** — the user's "action" is to highlight + copy + paste it into a terminal. The `St.Entry` therefore serves the role of a CTA: it has the visual prominence (focus ring in accent colour, monospace font drawing the eye) without being a button.

**Why not a button:** EGO explicitly rejects extensions that spawn subprocesses (PITFALLS.md §10 + CONTEXT.md D-13: "No button that runs commands. EGO rejects extensions that spawn subprocesses; we keep this honest by making the user run it themselves"). A copyable command is the GNOME-native, EGO-compliant equivalent of "click here to fix" — same user outcome, zero privilege escalation.

For purposes of the Copywriting dimension check: **the primary CTA copy is the literal command string** `systemctl --user enable --now usbeehive` — a verb (`systemctl`) followed by a verb-phrase (`enable --now`) followed by a target noun (`usbeehive`). It is specific, actionable, and not generic.

### Empty / Error states (Dimension 1 explicit)

| State | Heading | Body / solution path |
|-------|---------|----------------------|
| Empty: zero devices, daemon running | `No USB devices attached` | (no body — not an error; user has nothing to do) |
| Empty: daemon not running | `usbeehive daemon not running` | `Run this command, then this list will populate automatically:` + selectable `systemctl --user enable --now usbeehive` |
| Error: D-Bus call fails after daemon was up | (no UI string — silent recovery) | The store keeps the last good snapshot; `logError` writes to journal once (PITFALLS.md §6 log volume); next signal triggers a fresh `ListDevices`. No flash-of-error in the popover — Phase 1 deliberately prefers stale-but-coherent UI over a transient error message that the next signal would erase a few hundred ms later. |
| Error: introspection / proxy construction fails at `enable()` | (no UI string — silent) | `logError` once; the empty state appears as if the daemon were not running (the symptom is functionally identical). |

### Destructive actions

**None in Phase 1.** Verified by walking the component inventory: no button widgets, no `delete` / `remove` / `clear` affordances, no GSettings writes. Confirmation copy is therefore N/A. Phase 2's per-port mute "Don't notify for this port" action is destructive-adjacent (it suppresses future notifications) but lives outside Phase 1's surface.

## Interaction & Live-Update Contracts

Anchor: `<a id="interactions"></a>`

### Hotplug — adding a device while popover is closed

- **Tile subtitle** re-derives within ~150 ms of the trailing-edge debounce (CONTEXT.md D-10). User sees the subtitle update silently with no animation. **No fade, no pulse.** The Shell's own widgets don't animate `subtitle` changes; USBee must not either.

### Hotplug — adding a device while popover is open

- The popover is **NOT** rebuilt mid-open. Per CONTEXT.md D-11, rows are populated lazily on `open-state-changed`. A device added while the popover is currently open will appear the **next** time the user opens it. **This is intentional**: it prevents flicker mid-read and is the same trade-off GNOME Shell's own `backgroundApps.js` makes. The subtitle DOES update live, signalling that something changed; if the user closes-and-reopens, they see the new row.
- **Document this in code review:** an executor may be tempted to "fix" this by also rebuilding on `devices-changed`. Resist — it's a feature, not a bug.

### Hotplug — removing a device while popover is open

- Same as above: the row stays visible until the popover is closed and reopened. Subtitle re-derives live.

### Daemon disappears while popover is open

- The popover **transitions to the empty state on the next open** — not mid-open. The subtitle updates immediately to `Daemon not running`. If the user is staring at the open popover when the daemon dies, the listed devices remain (stale) until they close + reopen. Same rationale as above.
- **Alternative considered + rejected:** swapping mid-open. Rejected because (a) the Shell does not provide a smooth transition primitive for `PopupMenuSection.removeAll()`; the visual would be a hard jump that looks like a glitch, and (b) it requires the popover to subscribe to `lost` independently, which violates D-11's "lazy populate" invariant.

### Daemon appears while popover is closed

- Subtitle re-derives within ~150 ms (debounced) showing the fresh state. Tile feels "alive" again with no user action — STATE-02.

### Daemon appears while popover is open (empty-state visible)

- Same lazy rule: the empty-state row remains until close+reopen. But the subtitle changes immediately, telling the user "something happened — open me again."

### Click on the empty-state `St.Entry`

- Focus the entry. **Do not** auto-select-all the text. Standard Shell `St.Entry` keyboard behaviour: arrow keys move the cursor, Ctrl+A selects all, Ctrl+C copies. The entry is read-only (`clutter_text.editable = false`) so typing has no effect.
- **No "Copied!" toast.** This is the Shell; toasts would be a Phase-2 notification surface. The user knows they pressed Ctrl+C.

### Click on a device row

- Rows are **non-interactive** in Phase 1 (`reactive: false, can_focus: false`). Clicking them does nothing. The popover does not close on row-click. This matches how Wi-Fi / Bluetooth list rows behave when they are pure information without a paired action.

### Click on the tile itself

- Standard `QuickMenuToggle` behaviour: clicking the body of the tile opens the popover. There is no on/off toggle for USBee (`toggleMode: false` per RESEARCH.md §Example 2). The tile is informational.

### Keyboard

- Tile is keyboard-reachable via the standard Quick Settings tab order (Shell-managed; USBee does not configure).
- Inside the popover, only the `St.Entry` is focusable. Tab cycles to it; Shift+Tab returns to the tile.

### Visual stability requirement (debounce, CONTEXT.md D-10)

- The 150 ms trailing-edge debounce + the lazy popover rebuild together guarantee: **no widget repaints faster than ~6 Hz under burst hotplug**. The auditor should run RESEARCH.md Test 5 (combined stress run) and watch for sub-100ms repaints — any are a regression.
